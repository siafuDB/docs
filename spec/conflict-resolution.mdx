Two devices can change the same vertex while offline. Conflict resolution decides which change wins. Every device must reach the same answer from the same ops, so the rules are deterministic.

## Status

**Draft.** Ordering by hybrid logical clock and op id is implemented in the wire format. The resolver that applies the strategies below has not been updated to it yet: the existing code still compares vector clocks. Treat the strategies as the target design.

<Warning>
  Earlier versions of this page and of the research notes described two different last-writer-wins rules: "highest wall clock wins" and "higher vector clock wins". The second has no meaning for concurrent changes, because concurrent clocks have no order. The rule on this page replaces both.
</Warning>

## Causality

Each op lists the heads its writer had applied (`deps`) and its author's previous op (`prev`). See [Mutation format](/spec/mutation-format).

- **Happens-before.** Op B names op A, directly or through its dependencies. Apply A, then B. There is no conflict.
- **Concurrent.** Neither names the other. If they touch the same property, that is a conflict, resolved by strategy.

Signed ops carry no vector clocks. A vector clock grows with every device a fragment has ever seen and cannot be pruned once signed.

## Ordering concurrent ops

Concurrent ops are ordered by their hybrid logical clock, then by op id:

1. Higher `wall_ms` wins.
2. On a tie, higher `counter` wins.
3. On a tie, the larger op id wins.

Op ids are content hashes, so step 3 always gives one answer on every device.

A hybrid logical clock uses wall time but never moves backwards. A receiver does not apply an op whose timestamp is more than 5 minutes ahead of its own clock, and does not merge that timestamp into its own clock. This limits how far a wrong or dishonest clock can win. Old timestamps are never rejected.

## Strategies

Strategies are declared on the schema or the fragment.

| Strategy          | When to use              | Behavior                                                                                                |
| ----------------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `LastWriterWins`  | Personal devices         | Per property, the op that orders last wins.                                                             |
| `MergeProperties` | Collaborative content    | Changes to different properties both apply. Changes to the same property fall back to `LastWriterWins`. |
| `RejectIncoming`  | Authoritative fragments  | The incoming op is not applied. A notification may be emitted.                                          |
| `AcceptIncoming`  | Caches and read replicas | The incoming op wins. Local state is discarded.                                                         |

## Deletes

A delete that is concurrent with an edit of the same vertex needs a stated rule, or devices diverge. The target rule is remove-wins: the vertex stays deleted, and a tombstone records the delete. Tombstones are not garbage-collected in v0, because collecting them lets an offline device bring deleted data back.

## Authority interaction

See [Authority](/concepts/authority). A write against a `Referenced` vertex either fails or becomes a **change proposal** that the authoritative fragment may accept, reject, or merge.

Change proposals are not in wire format v0. Authority is also local state today: nothing in a signed op states who may write a vertex. Both are open work.

## Open questions

- User-visible conflict markers when `MergeProperties` cannot reconcile.
- How an op proves its author may write the target vertex.
