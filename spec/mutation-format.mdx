A mutation travels on the wire as a signed **op**. This page summarises wire format v0. See [Mutations](/concepts/mutations) for the concepts.

## Status

**Draft, v0.** The format on this page is implemented in the `gsp-wire` crate, which is not published yet. It replaces the earlier draft on this page. Breaking changes are still possible before 0.1.0.

<Warning>
  The earlier draft specified UUIDv7 ids, a single optional Ed25519 signature, and a vector clock per mutation. None of those are part of v0. If you built against the earlier draft, treat it as withdrawn.
</Warning>

## Op fields

| Field         | Type                 | Notes                                                                                                       |
| ------------- | -------------------- | ----------------------------------------------------------------------------------------------------------- |
| `format`      | uint                 | Envelope version. `0` in v0. Changes only for structural changes, never for a new algorithm.                |
| `hash_alg`    | uint                 | Registry id of the hash used for this op's id.                                                              |
| `fragment_id` | bytes                | The fragment the op belongs to. The signature covers it, so an op cannot be replayed into another fragment. |
| `author`      | multihash            | Id of the author's key-log genesis entry.                                                                   |
| `seq`         | uint                 | Position in the author's chain. Starts at 1.                                                                |
| `prev`        | multihash or null    | Id of the author's op at `seq - 1`. Null only when `seq` is 1.                                              |
| `hlc`         | `[wall_ms, counter]` | Hybrid logical clock. Orders concurrent writes.                                                             |
| `deps`        | list of multihash    | Heads the writer had applied when it wrote the op. This is the causality record. At most 64.                |
| `payload`     | any                  | The change itself. Opaque to the wire layer in v0.                                                          |

## Ids

An op's id is the hash of its canonical bytes, with the hash algorithm inside the id. Ids are not UUIDs. A receiver recomputes the id from the bytes it received and never by re-encoding.

## Encoding

Deterministic CBOR (RFC 8949, section 4.2). Map keys are text strings only. A decoder re-encodes what it read and rejects input whose bytes differ.

## Signatures

An op carries a list of signatures. Each entry names its algorithm by registry id.

- A signature covers a domain label (`gsp/v0/op`), the fragment id, and the op id. The parts are length-prefixed.
- An author's policy sets which algorithms are required. A hybrid author needs both Ed25519 and ML-DSA-65. Removing either signature makes the op invalid.
- Policy comes from the author's key log, not from the op. The key log is a signed, hash-chained list of add-key, revoke-key, and set-policy entries.
- A key revoked at `seq` N stays valid for ops at or below N and is rejected above N.

Verification returns one of three verdicts:

| Verdict      | Meaning                                                                                 | Applied?                        |
| ------------ | --------------------------------------------------------------------------------------- | ------------------------------- |
| Valid        | Structure, chain, and every required signature check out.                               | Yes                             |
| Unverifiable | An unknown algorithm or format, an unknown author or key, or a timestamp too far ahead. | No. Retained for a later retry. |
| Invalid      | Tampered, wrongly signed, or structurally wrong.                                        | No                              |

## Algorithm registries

Ids are numeric and append-only.

| Registry     | Id  | Name               | In v0                |
| ------------ | --- | ------------------ | -------------------- |
| Signature    | 1   | Ed25519            | Implemented          |
| Signature    | 2   | ML-DSA-65          | Implemented          |
| Hash         | 1   | BLAKE3-256         | Implemented, default |
| Hash         | 2   | SHA3-256           | Implemented          |
| Hash         | 3   | SHA-256            | Registered only      |
| Key exchange | 1   | X25519             | Registered only      |
| Key exchange | 2   | ML-KEM-768         | Registered only      |
| Encryption   | 1   | XChaCha20-Poly1305 | Implemented          |
| Encryption   | 2   | AES-256-GCM        | Registered only      |

## Equivocation

Two different valid ops with the same author and `seq` are an equivocation. The pair is a proof that a third party can check.

## Batches

A batch is a signed list of complete signed ops, at most 1024. The batch signature authenticates the sender, the set, and its order as a unit. It does not replace each op's own signatures: a valid batch can still contain ops that are not valid.

## What a relay sees

Ops are signed first, then encrypted with XChaCha20-Poly1305. A relay sees ciphertext and an opaque header. It does not see the author, the payload, or the signatures.

## Known limits of v0

- The payload has no schema yet. The operation types in [Mutations](/concepts/mutations) are the planned payload schema.
- The handshake and hybrid key exchange are registered but not implemented.
- The ML-DSA implementation is a 0.1 release and has not been audited. The hybrid rule with Ed25519 is the mitigation.
- Key-log forks have no proof format or resolution rule.

## Open questions

- **Author identity.** v0 identifies an author by the hash of its key-log genesis entry, not by a DID. Binding a DID to that id is undecided.
- Compression of large payloads.
- Schema versioning inside the payload.

These are tracked in the [Decision log](/research/03-decision-log).
